# 삼성 헌터스 2.0 개발 시작점

기존 `hunters_old`의 오더 저장 형식을 유지하면서 모바일 화면과 오더 모델을 분리한 작업 디렉터리입니다. 운영 사이트와 운영 데이터는 변경하지 않았습니다.

## 실행

Node.js 24에서 다음 명령을 실행합니다.

```powershell
node dev-server.js
```

브라우저에서 `http://127.0.0.1:8765`를 엽니다. 로컬 화면은 데모 선수·오더를 사용하며 저장 비밀번호는 `demo`입니다. 저장 데이터는 서버 메모리에만 남고 재시작하면 초기화됩니다. 운영 API에는 연결되지 않습니다. 테스트는 `node --test`로 실행합니다. 별도 프론트엔드 패키지 설치는 필요하지 않습니다.

`index.html`을 파일 탐색기에서 직접 열어 `file:///...` 주소로 접속하면 브라우저가 JavaScript 모듈을 차단할 수 있어 버튼이 작동하지 않습니다. 반드시 위 로컬 주소로 접속하세요.

오더 작성 중에는 오더명과 참가 선수·포지션·타순 변경이 브라우저 저장 공간에 자동 저장됩니다. 같은 브라우저에서 다시 접속하면 **이어쓰기**로 복원할 수 있고, **초안 삭제**로 지울 수 있습니다. 초안은 해당 브라우저에만 남으며 브라우저 데이터를 삭제하거나 다른 기기에서 접속하면 복원할 수 없습니다. 서버 저장에 성공하고 재조회까지 끝나면 로컬 초안을 지웁니다.

선수 화면에서는 기존 선수의 등번호와 포지션을 수정하거나 새 선수를 추가할 수 있습니다. 저장할 때 선수 전체 목록을 updatePlayersV2로 보내고 다시 조회합니다. 기존 오더가 이름으로 선수를 참조하므로 기존 선수의 이름 변경과 삭제는 이 화면에서 지원하지 않습니다. 운영 화면의 선수 저장은 배포된 V2 쓰기 API를 사용합니다.

## 데이터 계약

`js/order-model.js`가 기존 오더의 `players`, `positions`, `startingList`(1~9번과 투수 행), `excludedPlayers`를 읽고 저장용 형식으로 다시 만듭니다. 선수 식별은 현재 운영 데이터와 같이 **이름**을 사용합니다. 이름이 바뀌거나 중복되면 기존 오더를 해석하기 어려우므로 선수 ID 도입은 별도의 데이터 이전 작업으로 다뤄야 합니다. 같은 선수가 투수(P)와 지명타자(DH)를 겸하는 기존 오더도 읽고 저장할 수 있으며, 다른 포지션의 중복 배정은 거부합니다.

운영 데이터는 Firebase Cloud Functions에서 Google Sheets의 `선수DB`, `설정`, `Orders` 시트를 읽고 씁니다. `js/config.js`의 `READ_API_BASE`는 배포된 화면에서 운영 조회 API를 가리키고, 로컬 개발 화면에서는 데모 API를 가리킵니다.

## 저장 API 연결 전 준비

새 `firebase/functions-v2/`는 별도 `hunters2` codebase로 분리했습니다. `saveOrderV2`, `updatePlayersV2`, `deleteOrderV2`가 요청마다 서버에서 비밀번호를 검증합니다. 기존 운영 Functions와 분리된 `hunters2` V2 함수는 `hunters-2026` 프로젝트에 배포됐습니다. `js/config.js`는 로컬에서는 데모 API를, 운영 화면에서는 배포된 V2 쓰기 API를 사용합니다. `firebase/functions/`는 이전 단계의 참고 코드이며 현재 `firebase.json`의 배포 대상이 아닙니다.

배포 후에는 다음을 확인해야 합니다.

1. Firebase Functions의 기본 서비스 계정에 Google Sheets 접근 권한을 부여한다. 별도 `service-account.json`은 저장소에 포함하지 않는다. 기존 디렉터리에도 해당 파일은 없었다.
2. `hunters2` codebase가 `hunters-2026`에 배포됐고, V2 쓰기 함수가 비밀번호 누락 또는 오류를 거부하는지 확인했다. 기존 codebase는 배포 대상에 넣지 않는다.
3. 새 함수 주소의 공통 부분을 `WRITE_API_BASE`에 설정하고 운영 화면에 연결한다.
4. 실제 오더의 저장 전후 데이터를 비교하고, 모바일에서 선수 이동·교체·투수·대기 명단을 확인한다.

새 codebase만 배포하려면 `firebase` 디렉터리에서 `firebase deploy --only functions:hunters2 --project PROJECT_ID`를 실행합니다. PROJECT_ID는 로그인 후 `firebase projects:list`로 확인한 값으로 바꿉니다. 함수 배포 런타임은 Node.js 22이며 로컬 개발·테스트는 Node.js 24에서도 실행할 수 있습니다. Firebase CLI 인증 후 `hunters2` 배포를 완료했습니다.

선수 목록 저장은 서버에서 빈 목록·중복 이름·잘못된 포지션 값을 거부하고, Google Sheets 단일 batchUpdate 요청으로 기존 목록을 교체합니다. 배포 후 Sheets 권한과 실제 저장·재조회를 확인해야 합니다.

새 쓰기 API 요청 형식은 `saveOrderV2: { orderName, payload, password, expectedSavedAt }`, `updatePlayersV2: { players, password }`, `deleteOrderV2: { name, password }`입니다. 새 오더의 `expectedSavedAt`은 `null`, 기존 오더는 조회한 `savedAt` 값입니다. 서버는 값이 달라졌으면 409를 반환해 덮어쓰기를 막습니다. 별도 함수 이름이므로 배포해도 기존 화면의 함수 호출은 바뀌지 않습니다. 기존 V1 쓰기 함수는 여전히 서버 인증이 약하므로 최종 전환 때 폐기하거나 보호해야 합니다.

## 현재 범위

홈, 오더 목록·상세, 기존 `?orderName=` 링크, 선수 목록, 그라운드 중심 편집, 포지션별 선수 선택, 타순·참가·대기·제외 선수 조작을 구현했습니다. 상세 화면에서 링크 공유와 PNG 이미지 저장을 할 수 있고, 작성 중인 초안도 이미지로 저장할 수 있습니다. 기존 오더명은 자유 입력 문자열이라 경기 일시와 상대팀을 별도 항목으로 표시하지 않습니다. PWA와 관리자 화면 이전은 다음 단계입니다.




## 관리자 기능

GitHub Pages 운영 화면의 **선수** 메뉴에서 이름순·등번호순 정렬, 선수 추가·수정·삭제를 사용할 수 있습니다. 선수 이름을 변경하면 기존 Orders 데이터의 이름 참조도 함께 갱신됩니다. 기존 오더에서 사용 중인 선수는 삭제할 수 없습니다. 오더 목록의 삭제 버튼과 선수 화면의 **비밀번호 변경** 버튼은 관리자 비밀번호를 확인한 뒤 V2 API를 호출합니다.

## 선수 투구·타격 유형

선수 관리에서 각 선수의 투구 유형과 타격 유형을 `우` 또는 `좌`로 선택할 수 있습니다. 기존 선수는 값이 비어 있는 상태로 표시되며, 저장하면 Google Sheets 선수DB의 새 `throws`, `bats` 열에 반영됩니다.

## 선수 표 일괄 편집

선수 표에서 이름, 배번, 투구/타격, 포지션을 직접 수정한 뒤 **전체 저장**을 누릅니다. 수정한 행은 색으로 표시되며 검색과 열 정렬 후에도 입력값이 유지됩니다. 선수 추가와 삭제도 전체 저장 시 함께 반영됩니다. **원래대로**는 저장 전 변경을 버리고 최신 DB를 다시 불러옵니다.

일괄 저장 요청은 `updatePlayersV2: { players, expectedPlayers, originalNames, password }`입니다. `expectedPlayers`는 조회 당시 목록이고 `originalNames`는 각 행의 원래 이름(신규 선수는 null)입니다. 서버는 변경된 목록을 감지하면 재조회를 요청하며, 이름 변경에 따른 기존 오더 참조와 선수 DB를 한 번의 Sheets batchUpdate로 저장합니다. 기존 오더에서 사용하는 선수의 삭제는 거부합니다. 운영 함수 소스는 `firebase/functions-v2`입니다.

## 오더 화면 구성

기존 프로젝트처럼 오더 미리보기(그라운드·선발·대기 명단) 옆에 오더 목록을 표시합니다. 목록은 10개씩 페이지를 이동하며, 수정·캡처·링크 복사·공유를 사용할 수 있습니다. 모바일에서는 목록과 미리보기를 세로로 배치합니다.

작성 화면은 참가 명단 / 그라운드와 선발·대기 명단 / 포지션별 주·부 선수 명단으로 구성합니다. 그라운드 또는 선발 표의 선택창에서 직접 배치할 수 있고, 주·부 명단에서 이름을 눌러 배치하거나 해제할 수 있습니다. 외야수는 LF/CF/RF를 선택합니다. 대기 명단의 이름을 누르면 제외·복귀를 전환합니다. 좁은 화면에서는 각 영역을 세로로 배치하며 초안 이어쓰기와 기존 오더 링크는 유지됩니다.

## 공통 오더 이미지 캡처

조회·작성 화면 모두 현재 오더 데이터로 읽기 전용 패널(오더명, 그라운드, 선발·대기 명단)을 새로 구성해 PNG로 저장합니다. 오더 목록의 미리보기와 같은 렌더러를 사용하며 선택창과 작업 버튼은 포함하지 않습니다. 투타, 배치 음영, 제외 취소선과 테마를 유지합니다. 화면 크기와 관계없이 일정한 폭으로 출력하며 같은 데이터와 테마는 두 화면에서 같은 이미지를 만듭니다. `vendor/html-to-image.js`를 로컬에서 불러오므로 외부 CDN 연결은 필요하지 않습니다.

브라우저 이미지 비교 검증: 로컬 데모 서버 실행 후 `node scripts/verify-capture.cjs`. Windows의 `%TEMP%/hunters-browser-qa`에 `playwright`와 `pngjs`를 설치하고 Edge를 사용합니다. 테스트는 가상 API 데이터만 사용하며 실제 DB를 변경하지 않습니다.

## 경기일정으로 관리 (현재 버전)

오더명과 저장일자는 화면 및 관리 기준에서 사용하지 않습니다. 작성 시 경기일(달력), 경기시간, 상대팀을 입력하고, 목록은 **경기일정 / 상대팀 / 관리** 열로 표시합니다. 일정 형식은 `2026-09-20 (일) 12:00`입니다. 미리보기, 공유 제목, 캡처 이미지와 파일명, 초안도 경기정보를 사용합니다.

- 새 API: `getOrdersV3`, `getOrderV3?id=...`, `saveOrderV3`, `deleteOrderV3`.
- 저장 요청: `{ id, game: { date, time, opponent }, payload, expectedVersion, password }`.
- 신규 경기는 UUID를 사용하고, 일정·상대팀을 수정해도 ID를 유지합니다. 버전은 동시 수정 보호를 위한 내부 값이며 화면에는 표시하지 않습니다.
- 경기정보는 Orders의 JSON 데이터에 `game`으로 저장합니다. 기존 행은 호환을 위해 유지하며, 예전 이름 형식에서 확인 가능한 경기일과 상대팀을 복원해 표시합니다. 기록이 없던 경기시간은 **시간 미정**으로 표시하며 다음 수정 저장 시 입력합니다.
- 공유 링크는 `?game=ID`입니다. 예전 `?orderName=...` 링크도 읽기 호환으로 지원합니다.
- 운영 전환 과정에서 기존 경기 날짜·시간을 임의로 일괄 덮어쓰지 않습니다.

검증: `npm test`, 로컬 서버 실행 후 `node scripts/verify-game-schedule.cjs`, `node scripts/verify-capture.cjs`. 브라우저 검증은 임시 Playwright/PNGJS 설치 및 Edge가 필요합니다.
